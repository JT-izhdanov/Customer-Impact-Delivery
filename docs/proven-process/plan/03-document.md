## Customer Impact integration points

Document is where impact commitments get baselined alongside everything else — if they're not in the plan artifacts here, they don't exist in delivery:

- **Milestones include impact milestones.** The milestone definition already being finalized by PMO ("recognized by the customer... toward the Flag Plant") should distinguish *deliverable* milestones from **impact checkpoints**: baseline captured, adoption telemetry live, first VRR held, metric movement reviewed (doc 06 lifecycle). Since exit-gate deliverables are tracked as a 'Deliverable' type in Project Operations, VRRs and measurement artifacts become trackable objects, not intentions.
- **Backlog carries metric traceability forward.** User stories arrive from Discovery tagged to outcome metrics; prioritization then has an impact lens — stories that move the metric outrank nice-to-haves when scope pressure hits (and it always hits).
- **Governance plan covers off-metric drift within existing decision rights.** Decision rights, escalation, and ceremonies are agreed here — for impact engagements, record that on-plan-but-off-metric drift is raised by the PL (technical traceability) and handled by the PM as a delivery-governance matter, with the metric-owning executive informed (per the PM/PL standard's existing split — doc 11, no new decision rights). The stakeholder registry marks the **metric-owning executive** explicitly.
- **Adoption/Training approach is drafted here — make it measurable.** Extend the draft with usage-telemetry targets (Copilot dashboards, D365 usage, report consumption — doc 06), since adoption data is both VRR input and Microsoft incentive currency (research 01).
- **RAID log gets impact risks from day one.** Standard entries for impact engagements: baseline data unavailable, metric owner disengaged, customer's 50% not delivered (Block's contracting items from the Solution Meeting), adoption below telemetry targets. Each with a named owner — the RAID structure already demands it.
- **Change control protects the hypothesis.** The change-control approach should state: scope changes that materially affect the outcome metric trigger an Impact Hypothesis revision signed by the metric owner — so the VRR never measures against a target the project quietly renegotiated away.
